**Phase 1 — Auth & Tenancy (2026-08-08, Jeet)**

- `[2026-08-08]` **Invite mechanism: unguessable token + `accept_invite()` RPC, invitee never reads the `invites` table** — the invitee has to consume the invite *before* they belong to the tenant, when every tenant-scoped policy correctly excludes them. Opening read access on `invites` so they could find their own row would expose staff emails and roles per clinic. Instead the `token` (uuid v4, 122 bits, delivered out-of-band) is a capability, and a `SECURITY DEFINER` function does the lookup for them. Table stays admin-only
- `[2026-08-08]` **`accept_invite()` requires `email_confirmed_at IS NOT NULL`** — the email-match check is what stops a forwarded token being redeemed by the wrong person, and without confirmation that check is bypassable by simply signing up *as* the invited address. Confirmation is load-bearing, not hygiene (see risk in §6)
- `[2026-08-08]` **Stale invites are refreshed with a *rotated* token, not reused** — "resend invite" must kill the old link, otherwise it silently extends the life of a token that may have leaked
- `[2026-08-08]` **`profiles.role` / `profiles.tenant_id` / `tenants.tier` are not client-writable at all; column-level `GRANT`s enforce it** — an RLS `WITH CHECK` only sees the NEW row, so it cannot express "you may change role but not tenant_id". Granting `authenticated` UPDATE on `role` therefore lets *any* user run `update profiles set role='admin' where id=auth.uid()` and satisfy a self-update policy. `authenticated` now holds UPDATE on `profiles.full_name` and `tenants.name` only
- `[2026-08-08]` **Role assignment moved from a raw admin UPDATE to `admin_set_user_role()`** — consequence of the above. Deviates from phases.md/prompt, which described an RLS-gated update; that shape cannot be made safe
- `[2026-08-08]` **`tenants.tier` is deliberately not admin-writable** — an admin who could raise their own tier would unlock Tier 2/3 modules for free, making the tier gate cosmetic (rules.md §4.3). Tier changes are a platform-owner action via the dashboard (PRD §6.6)
- `[2026-08-08]` **RLS tenancy lookups go through three `SECURITY DEFINER` helpers (`current_tenant_id()`, `current_user_role()`, `is_tenant_admin()`)** — the obvious self-referencing policy on `profiles` throws `42P17 infinite recursion` and makes the table completely unqueryable. Reproduced empirically before settling on this. All three take no arguments and read only `auth.uid()`, so nothing a client sends can influence them (rules.md §1.2)
- `[2026-08-08]` **RPCs return a `jsonb {ok, code, message}` envelope instead of raising** — PostgREST maps an unrecognised SQLSTATE to HTTP 500, so raising would make "you already belong to a clinic" indistinguishable from "the database is down". Split is now: supabase-js `error` = transport/auth/RLS/bug, `data.ok === false` = explainable business rule (rules.md §3.3, §3.5)
- `[2026-08-08]` **Seed is a TypeScript script (`supabase/scripts/seed.ts`), not `seed.sql`** — GoTrue owns `auth.users`; SQL-inserted rows lack the expected password hash format and companion `auth.identities` row, so the accounts exist but cannot log in, which defeats the entire purpose of a dataset meant for multi-session RLS testing. Script drives the real RPCs, so seeding is itself an end-to-end flow check
- `[2026-08-08]` **`CANNOT_DEMOTE_LAST_ADMIN` guard added** — a tenant with zero admins can never invite anyone or change its own settings again, and only Jeet could repair it from the dashboard. Cheap to prevent, expensive to fix
- `[2026-08-08]` **Verification uses PGlite (real PostgreSQL 17.5 compiled to WASM) rather than `supabase start`** — Docker is unavailable on the dev machine and applying migrations to the hosted project needs a personal access token we don't have yet. Without this there would have been zero *executed* verification of ~700 lines of security-critical SQL. The harness reproduces Supabase's roles, `auth` schema and permissive default privileges; seams are documented in `supabase/tests/harness/supabase-preamble.sql`
- `[2026-08-08]` **Supabase CLI + PGlite added as devDependencies at the repo root, pinned exactly** — CLI is the documented migration tool (Architecture.md §8); PGlite exists solely for the offline test harness. Neither is a new backend/ORM/host, so rules.md §1.5 is not engaged

**Phase 2 — Core OPD Flow (2026-08-11, Jeet)**

- `[2026-08-11]` **Tax lives on the LINE ITEM (`tax_category` + `tax_rate`), and an invoice carries a rate-wise summary child table (`invoice_tax_lines`) — never a rate applied to a total.** A single OPD bill mixes a GST-exempt consultation (Notification 12/2017) with taxable medicines (5% after the Sept 2025 GST Council rationalisation, some life-saving drugs exempt). One blended rate on the total produces a *wrong* bill, not an imprecise one — it either taxes an exempt consultation or under-taxes medicine, and the error is invisible once summed. A DB constraint makes an inconsistent category/rate pair unrepresentable
- `[2026-08-11]` **`tenants.gst_registered` defaults to FALSE, and a non-registered tenant gets NO tax lines at all — a bill of supply, not a GST invoice showing zeros.** Whether a clinic charges GST depends on its registration, which depends on turnover (₹20 lakh threshold, ₹10 lakh in some special-category states). A solo doctor below it legitimately issues a non-GST bill. Printing zeroed tax boxes would misrepresent registration status. **This is a per-clinic business decision Jeet must confirm — see §6**
- `[2026-08-11]` **GSTIN is snapshotted onto each invoice at creation.** An invoice is a tax document; a clinic registering later or fixing a GSTIN typo must not retroactively rewrite invoices already handed to patients
- `[2026-08-11]` **`check_prescription_safety()` returns a severity per finding plus an explicit `status` of `complete` | `partial`, never a boolean.** Severity is what lets the UI be silent-by-default and interrupt only on high (PRD §6.1, rules.md §6.4) — a boolean would have made that decision on the frontend's behalf. `partial` exists because an empty findings array is ambiguous in the worst direction: it fires on unresolved drugs (`UNKNOWN_DRUGS`) **and on an empty allergy field** (`NO_ALLERGIES_RECORDED`), because a blank allergy history means nobody asked, not that the patient has none. Genuine failure is a third state (`ok:false, SAFETY_CHECK_UNAVAILABLE`)
- `[2026-08-11]` **`drugs` / `drug_interactions` deliberately have NO `tenant_id`** — a documented exception to rules.md §4.1. That rule governs tenant *business* data; this is shared reference data (paracetamol is paracetamol everywhere). Per-tenant copies would multiply storage, require N-fold corrections, and let clinics silently disagree about an interaction. Isolation is honoured in the other direction: RLS on, read-only to every client including admins, maintained only by migration/service_role
- `[2026-08-11]` **`drugs.interaction_generics` array added** so fixed-dose combinations match single-molecule interaction pairs. Indian prescribing is combination-heavy; matching on `generic_name` alone would mean 'ibuprofen + paracetamol' matches no pair and the ibuprofen–warfarin interaction is silently missed — a false negative of exactly the kind rules.md §3.4 warns about
- `[2026-08-11]` **`drug_interactions` pairs are stored in canonical order (`generic_a < generic_b`), enforced by CHECK.** Without it {warfarin, aspirin} and {aspirin, warfarin} are two rows and a single-ordering lookup misses the interaction
- `[2026-08-11]` **Prescriptions have a `draft` → `issued` lifecycle, and billing fires on `issued`, not per item insert.** Billing per insert breaks ordinarily: a doctor adds a line, mistypes, removes it — and the patient has already been charged for a drug never given. `issued` is the real chargeable event; items are frozen at that point
- `[2026-08-11]` **NO unique index on `patients.phone`.** Two cases break it: a walk-in with no number, and genuinely different people sharing one (a child on a parent's mobile). A hard constraint makes the second unregistrable and pushes the receptionist into inventing fake numbers, which corrupts data far worse than a duplicate. Instead: a generated `phone_normalized` (last 10 digits), soft detection in `register_patient()` returning `DUPLICATE_PATIENT` + the matching records, and an explicit `p_allow_duplicate_phone` override. INSERT is withheld from clients so the check cannot be bypassed
- `[2026-08-11]` **`patients.age_years` alongside nullable `dob`** — many Indian patients state an age, not a date of birth, and back-computing a DOB invents precision nobody gave
- `[2026-08-11]` **Composite FKs `(parent_id, tenant_id)` against a parent `unique (id, tenant_id)` on every Phase 2 child table.** Makes cross-tenant parenting *structurally* impossible rather than merely policy-blocked — the guarantee that survives a future RLS mistake. Verified by attempting the write as the table owner with RLS out of the picture
- `[2026-08-11]` **`clinical_notes` is readable by admin/doctor/nurse but NOT billing, while `prescriptions` IS readable by billing.** Billing does not need a diagnosis to raise an invoice, and a default front-desk grant on clinical notes is what DPDP alignment gets judged on (PRD §7). Prescriptions are the opposite: in an Indian clinic the pharmacy and billing counter are the same desk, and dispensing needs the drug list. Same minimisation principle, different answers
- `[2026-08-11]` **The billing auto-insert triggers are SECURITY DEFINER; nothing else in the write path is.** The user who triggers a charge is the wrong person to author it — a doctor deliberately has no INSERT on `billing_line_items`, so a trigger running as them would fail the policy and the consultation would go unbilled, which is the revenue leakage PRD §3 calls out. Every value written is derived server-side. This is the phase's only stated exception to the no-bypassing-RLS boundary
- `[2026-08-11]` **`check_prescription_safety()` and the two `get_*_for_pdf()` payload functions are SECURITY INVOKER, unlike the rest.** They need no elevated privilege — the caller can already read everything they touch — so least privilege is available and taken. A cross-tenant id simply resolves to nothing
- `[2026-08-11]` **PDF *data* assembly lives in Postgres (`get_prescription_for_pdf` / `get_invoice_for_pdf`), and the Edge Functions are thin renderers that forward the caller's JWT.** Keeps tenant-scoped access under RLS instead of tempting a service-role key inside Deno, and — decisively — means the compliance-sensitive part (totals, tax buckets, whose data) is testable in SQL without deploying anything
- `[2026-08-11]` **Envelope vs plain CRUD, decided per operation.** RPCs where there is branching or a side effect (`register_patient`, `check_in_patient`, `set_visit_status`, `issue_prescription`, `check_prescription_safety`, `create_invoice_for_visit`). Plain table operations for ordinary CRUD — notably **note-taking**, because rules.md §1.7 wants that path frictionless and an RPC that could reject something would work against the requirement
- `[2026-08-11]` **Migrations applied via `supabase db push --db-url` against the `aws-0-ap-south-1` pooler, not `supabase link`.** Only a DB password is available on this machine, not a personal access token; and the direct host `db.<ref>.supabase.co` is IPv6-only and unreachable from WSL. Wrapped in `supabase/scripts/db.ts` so the password comes from `.env` rather than a command line and is scrubbed from all output

**Phase 3 — Nurse Workflows & IPD Foundations (2026-08-11, Jeet)**

- `[2026-08-11]` **Every `vitals` measurement column is nullable, and the sane-range CHECKs are separate from that.** rules.md §1.7 is written about doctor-facing notes so its letter does not name this table, but the requirement underneath — never block a save over an incomplete field — applies harder. A nurse mid-round has pulse and temperature but no BP because the only cuff is two beds down. If any column were NOT NULL she cannot save what she has, and the realistic outcomes are both bad: the reading stays on paper, or a placeholder is typed. **An invented vital is worse than a missing one**, because a doctor reads it as fact off a trend graph. Impossible values are a different question and *are* refused (temperature 20–45 °C etc.) — nullability is about *incomplete* data, CHECKs are about a slipped decimal point
- `[2026-08-11]` **IPD state went into a new `visits.care_setting` column, NOT into `visits.status` — consciously superseding a Phase 2 prediction.** Both `opd-queue.md` §9 and the Phase 2 migration header said Phase 3 would extend `visits_status_valid` additively. It does not, and that constraint is untouched. `status` tracks the *consultation* lifecycle; admission is orthogonal. A patient can be admitted *and* mid-consultation on a ward round, so one enum forces impossible-to-name states into a single value and every "is this visit open" query would have to learn about IPD. Consequence: **discharge does not write `visits.status`**; "currently an inpatient" is `care_setting='ipd' and discharged_at is null`. `opd-queue.md` §9 corrected in place rather than silently
- `[2026-08-11]` **The "rounds data" trigger maintains only `visits.last_vitals_at` — a bare timestamp — and deliberately does NOT cache vitals *values* onto `visits`.** `visits` is readable by billing; `vitals` deliberately is not (same minimisation line as `clinical_notes`), and Postgres has no column-level RLS. Caching blood pressures onto `visits` would hand every vital sign to the front desk through the back door. Column GRANTs cannot save it either, because billing and doctor are the same DB role. So the values come from `vitals` through the `rounds_overview` view under the caller's own policies, and the only thing cached is the part that is both non-clinical and expensive to derive per row
- `[2026-08-11]` **That same denormalised column is what makes Realtime work, which is the real reason it exists.** Logical replication only emits a change for the row that changed. A new `vitals` row does not touch `visits`, so a `visits` subscriber — the rounds list, which needs patient/bed/admission state — would never hear about it. The trigger writing `last_vitals_at` is precisely what turns a nurse's entry into a push on the doctor's screen, i.e. phases.md's "no separate fetch step". It recomputes `max(recorded_at)` from the table rather than copying `NEW`, so back-entering an older observation cannot move freshness backwards
- `[2026-08-11]` **Tier 2 gates the IPD/bed surface only; `vitals`, `tasks`, `lab_orders` and `lab_results` are ungated.** Architecture.md §6 marks exactly one Phase 3 table tier-restricted (`beds — IPD bed tracking (Tier 2+)`). A solo Tier 1 clinic employing a nurse who takes vitals at the OPD desk is completely ordinary in India — that is triage, not inpatient care — and gating it would break OPD triage for exactly the pilot-sized clinic Phase 2 was built for. What genuinely presupposes a ward is beds, so that is where the gate goes. Enforced in **RLS *and* the RPCs** per rules.md §4.3: policies alone would not stop an admit against a bed that somehow exists, an RPC check alone would leave a direct PostgREST insert ungated
- `[2026-08-11]` **`beds` SELECT is deliberately NOT tier-gated, and `discharge_patient()` is deliberately NOT tier-gated.** If a tenant were downgraded to Tier 1 while a patient was in a bed, a gated read would make that bed vanish from every screen while they were still lying in it, and a gated discharge would trap them permanently with no in-app way out. A feature gate exists to stop a clinic *starting* to use a module it has not paid for, not to trap clinical state it already has. **Unwinding is always allowed** — asserted in the suites by lowering the tier mid-test
- `[2026-08-11]` **`beds.current_visit_id` and `visits.bed_id` are NOT mirrors, and the asymmetry is intentional.** `current_visit_id` is live occupancy and is cleared on discharge; `visits.bed_id` records which bed the admission used and is retained. A CHECK makes `status='occupied'` ⟺ `current_visit_id is not null`, and a partial unique index stops one visit occupying two beds — both hold even against a service-role write, so occupancy is trustworthy structurally rather than because the RPC is careful
- `[2026-08-11]` **No recurrence/scheduling engine for tasks — flat `due_at` plus exactly two one-shot triggers.** "Vitals every 4 hours" needs a recurrence rule, an occurrence generator, a downtime catch-up policy and a discharge story; disproportionate to a phase whose job is making the board real. Admission creates one baseline `vitals_due` card; a lab order creates one `sample_collection_due` card. Both idempotent via a partial unique index on `(tenant_id, source_type, source_id, task_type)`, because a duplicated card on a triage board costs a nurse real time
- `[2026-08-11]` **Recording vitals auto-completes the oldest pending `vitals_due` task.** Recording the observation *is* doing the task, and Design.md §8 asks for select/tap over typing — making the nurse tick a second card works against that, and a board full of stale cards that were in fact done is worse than no board
- `[2026-08-11]` **Medication administration: the scan code is a REQUIRED parameter and the three failure modes are three distinct codes.** Exactly one of the clinical "five rights" is mechanisable and is the reason barcode administration exists: **right patient**. `PATIENT_MISMATCH` (resolved to a different patient — the dangerous one), `PATIENT_CODE_UNRECOGNISED` (resolved to nobody: smudged band, mis-decode) and `SCAN_REQUIRED` (nothing supplied) are deliberately not collapsed, because "we could not tell" must never look like a pass (rules.md §3.4). There is **no client INSERT** on the table, so the check cannot be bypassed by a direct PostgREST call. `PATIENT_MISMATCH` names neither patient — the nurse is at the wrong bedside and the remedy is to stop, not to be handed a second patient's identity
- `[2026-08-11]` **Duplicate doses are soft-detected and overridable, not blocked by a constraint.** `prescription_items.frequency` is free text from Phase 2 (`'TDS'`), so one item legitimately means three doses a day — a unique index would be *wrong*, not strict. `ALREADY_ADMINISTERED` returns the previous administration plus `can_override`, the same shape `register_patient()` uses for duplicate phones and for the same reason: a hard constraint would make a legitimate action impossible and push staff into working around the system
- `[2026-08-11]` **The critical-value flag is TWO non-nullable fields (`is_critical` + generated `requires_manual_review`), never one boolean and never a nullable one.** A lone `is_critical=false` cannot distinguish "checked and normal" from "no thresholds on file", which is a lie by omission in a safety path. A nullable boolean was considered and rejected because Phase 2 already learned that lesson with `requires_acknowledgement: null`. `critical_check_status` carries five values (`evaluated` / `no_reference` / `unparseable_value` / `unit_mismatch` / `evaluation_failed`); only `evaluated` means the comparison happened, and two CHECKs make `is_critical` unsettable without it. **`is_critical=false` + `requires_manual_review=false` is the only reassuring combination**
- `[2026-08-11]` **Unit compatibility is stated per analyte in `lab_critical_ranges.unit_aliases`, not by a global rule.** mEq/L and mmol/L are numerically identical for a monovalent ion like potassium and differ by a factor of two for a divalent one like calcium, so a global "meq == mmol" shortcut would be right for some rows and dangerously wrong for others. Same shape as `drugs.interaction_generics`: make it data, not parsing
- `[2026-08-11]` **Lab ordering is a plain INSERT, not an RPC**, because Architecture.md §3 describes an insert and there is nothing to decide at insert time. The three fan-out effects (billing line at ₹0, nurse collection card, Realtime) are triggers, so they fire whichever way the row arrives — including a future HL7 importer. Same reason the critical flag is set by a BEFORE trigger rather than inside `record_lab_result()`: the flag must be a property of the row, not of the code path that produced it
- `[2026-08-11]` **A lab order's auto-charge lands at ₹0 rather than being omitted.** There is no lab price list in the schema, and Phase 2 settled the identical question for a drug with no MRP: a visible zero line that billing prices is honest, while silently omitting the charge is the revenue leakage the whole auto-capture mechanism exists to prevent. Cancelling an order withdraws the pending line, and reports `billing_line_invoiced` when it is already on an issued invoice, since a tax document cannot be silently rewritten
- `[2026-08-11]` **`critical_lab_alerts` and the alert payload carry `patient_number` but NO patient name, by construction.** The same shape feeds the (undeployed) notification dispatcher, and that path will eventually terminate at WhatsApp or SMS. A payload that never contains a name cannot leak one into a third party, whatever a future integration does (rules.md §1.3)
- `[2026-08-11]` **`lab_results` carries acknowledgement columns + `acknowledge_critical_result()`.** phases.md's DoD says critical values must "trigger visible alerts, not passive queue entries", and without acknowledgement that claim is unfalsifiable on the server. With it, an unacknowledged critical result is an outstanding obligation with a name attached once someone clears it. Billing cannot acknowledge — clearing a clinical alert is a clinical act
- `[2026-08-11]` **Both Phase 3 views are `security_invoker`.** A view executes with its owner's privileges by default, and the owner here is `postgres`, which is not subject to RLS — so a plain view over these tables would be a perfect cross-tenant leak dressed up as a convenience. Asserted in the catalogue check because losing the option would break nothing visibly
- `[2026-08-11]` **`rounds_overview` returns the latest known NON-NULL value per measurement, not the newest `vitals` row** (fixed in `20260811071200` after the remote suite caught it). Returning the newest row contradicted the nullable-measurement design: a temperature recorded at 10:00 vanished the moment a BP-only row was saved at 10:05. Now a NULL there means "never recorded this encounter" and nothing else, and `vitals_component_times` gives the per-field timestamp so a composite card is detectable
- `[2026-08-11]` **`npm run db:query` / `verify:catalog` added.** Some guarantees live in the Postgres catalogue and are invisible to supabase-js entirely — Realtime publication membership, `security_invoker`, whether a REVOKE landed, whether RLS is actually *enabled*. All four fail silently. `psql` is not installed and the Management API needs a PAT, so the CLI's own query command is routed through the existing scrubbed `--db-url` wrapper

**Phase 4 — Admin, Multi-Branch & Tier 3 Groundwork (2026-08-11, Jeet)**

- `[2026-08-11]` **User deactivation is enforced in the seven tenancy helpers, not in ~100 policies.** `profiles.is_active` is checked inside `current_tenant_id()`, `current_user_role()`, `is_tenant_admin()`, `is_tenant_staff()`, `has_tenant_role()`, `current_tenant_tier()` and `tenant_has_tier()`. `current_tenant_id()` returning NULL does almost all the work: every tenant-scoped policy compares `tenant_id = current_tenant_id()`, and `tenant_id = NULL` matches no row — so one function change revokes all data access with nothing to keep in sync. `profiles_select_self` is deliberately left alone so a deactivated user can still read their own row and the UI can tell them *why* everything is empty rather than looking like data loss. The catalogue suite now asserts all seven still contain the predicate, because a future rewrite dropping it would disable deactivation with no error anywhere
- `[2026-08-11]` **Deactivation does NOT end the session, and that is documented rather than papered over.** Database access stops from the next statement; the JWT stays valid until it expires (~1h). Postgres cannot revoke a GoTrue session — that needs the Auth Admin API and a service-role key, and embedding one in the database to do it would breach rules.md §1.1/§1.4 to improve on something already fully mitigated at the data layer. Client-side forced sign-out is specified for Prince in `user-management.md` §4 and recorded as a risk in §6
- `[2026-08-11]` **`CANNOT_DEACTIVATE_SELF` is unconditional, even when other admins exist.** An admin who deactivates themselves is locked out instantly and cannot undo it — reactivation needs an admin and they have just stopped being one. Far more likely a misclick on the wrong row than an intent. `CANNOT_DEACTIVATE_LAST_ADMIN` is a separate guard counting **active** admins, because Phase 1's `CANNOT_DEMOTE_LAST_ADMIN` counts by role alone; without both, each could be satisfied while leaving the clinic with nobody able to act
- `[2026-08-11]` **`admin_set_user_active()` takes NO free-text reason.** A reason attached to revoking a named individual's access invites HR commentary ("dismissed for…") into a permanent, admin-readable compliance table with no erasure path. The log records the fact, the actor and the time, which is what "who changed what, for compliance" asks for. Flagged for Jeet to revisit if a pilot clinic needs otherwise
- `[2026-08-11]` **⚠️ THE AUDIT-LOG PII BOUNDARY: `changes` records field NAMES always, and VALUES only for an allow-list of non-personal columns.** Allow-listed: `profiles.{role,is_active,tenant_id,deactivated_at}`, `tenants.{name,tier,gst_registered,gstin,gst_state_code,default_consultation_fee}`, `invites.{role,expires_at,accepted_at,accepted_by}`. Everything else records `{changed:true, redacted:true}`. **The default is redaction**, so a column added to an audited table is redacted automatically rather than leaking until someone remembers. `invites.email` is excluded (personal data, already on the row) and `invites.token` is excluded (a live capability that must not be copied into a longer-lived, differently-guarded table)
- `[2026-08-11]` **Clinical content is excluded from the audit log even though an admin can already read `clinical_notes`.** The deciding reason is permanence: notes get corrected, patients get merged, data gets erased, and DPDP alignment (PRD §7) includes correction and erasure — so a `changes` blob holding the prior text of every clinical edit is an un-erasable shadow copy of exactly the data those obligations cover, sitting in a table nobody thinks of when honouring a deletion request. Secondary reasons: it would be a second, less-guarded copy that any future widening of audit access silently carries along, and unbounded growth of the most sensitive content for no clinical purpose
- `[2026-08-11]` **The redaction allow-list lives in `audit_diff()`'s function body, not a config table.** A table would be editable by service_role, meaning the boundary between "log this value" and "log that it changed" could move without a migration, a diff or a review. This is security policy, so it belongs where it cannot be quietly reconfigured
- `[2026-08-11]` **Audit rows come from TRIGGERS, not from the RPCs.** `admin_set_user_role()` and `admin_set_user_active()` could each log their own event and it would read more naturally, but triggers catch every path — a service-role backfill, a dashboard edit, a future migration, a second RPC someone adds later. An audit log that only records the writes somebody remembered to instrument is the one you cannot rely on. Accepted cost: a trigger knows *what* changed, not *why*, so `action` is derived from the diff
- `[2026-08-11]` **`record_audit_event()` never raises.** Actor resolution is wrapped, and a failure degrades to `actor_is_system = true` with the SQLSTATE preserved under a reserved `_audit_note` key. An audit trigger that could abort the transaction it observes would make the log a liability rather than a safeguard. This is not a swallowed error (rules.md §3.2) — the row is still written and the cause is recoverable, same discipline as `flag_lab_result_critical()`
- `[2026-08-11]` **Dashboard metrics are VIEWS, not RPCs — including for date ranges.** PostgREST filters a view like a table, so `.gte('activity_date', from)` gives arbitrary ranges with no server-side parameter, and sorting, pagination and generated types all keep working. An RPC would have bought nothing and cost all three. Admin-only is expressed as `where public.is_tenant_admin()` **inside each view body**, because a view cannot carry an RLS policy — so a non-admin gets **zero rows, not an error**, which Prince has to handle
- `[2026-08-11]` **A clinic "day" is the UTC calendar date across every daily metric, inherited from `visits.visit_date`.** Phase 2 set that with `current_date` on a UTC session, so a clinic day runs **05:30 IST → 05:30 IST**. The dashboard deliberately inherits the imperfection rather than bucketing patients/revenue by `Asia/Kolkata` while visits bucket by `visit_date` — panels disagreeing with each other and with the queue screen staff use all day is worse than the boundary itself. One definition of "day", even an imperfect one, beats two. Proper fix (per-tenant timezone + changing what `check_in_patient()` writes, which changes queue numbering) is a Phase 5 item
- `[2026-08-11]` **"Staff utilization" is reported as ACTIVITY COUNTS plus real consulting minutes, and the contract says it is not utilization.** There is no roster, no shifts, no clock-in and no contracted hours, so the denominator does not exist and cannot be inferred; building one would mean inventing a time-tracking module nobody asked for. `visits.consultation_started_at`/`consultation_ended_at` DO both exist, so **consulting minutes is a genuine time measure**, not a proxy — it is the number worth showing. NULL-safe: a visit missing a stamp contributes nothing rather than counting as zero minutes, and `consultations_untimed` reports how much is unmeasured. The view exposes counts and minutes only — no patient identity, no clinical content — so a management metric cannot become a back door into records
- `[2026-08-11]` **`admin_occupancy_current.occupancy_pct` is NULL, not 0, when a clinic has no beds.** "0% occupied" and "no ward exists" are different statements and a gauge reading 0% for a clinic with no ward is a lie. The view is built from `tenants` outward so a Tier 1 clinic still gets one row of zeros rather than no row, letting the UI say "no beds configured" instead of distinguishing an empty result from a failed query. Not tier-gated, following the `beds` SELECT precedent
- `[2026-08-11]` **Reconciliation returns one row per FINDING with a `severity` that is part of the contract.** The end-of-shift question is "is anything off, and what" — one list, sorted by how much it matters. Three separate views would make the frontend ask three questions and merge the answers. `high` = money is definitely wrong; `warning` = money is probably being lost; `info` = a charge raised today, normal. Without severity a genuinely broken invoice sorts alongside a charge four minutes old
- `[2026-08-11]` **The invoice sum-mismatch check exists precisely because it "should be impossible".** While `create_invoice_for_visit()` is the only writer of invoice totals it can never fire — which is the point. The paths that bypass it are real: a service-role backfill, a dashboard edit, a future consolidated-invoice feature, or a bug in a later revision of that RPC. A reconciliation view that only catches the errors we already thought of is not one. Compared with a 0.01 tolerance because line amounts are individually rounded to paise; `grand_total` is generated so it cannot drift and is not checked
- `[2026-08-11]` **Tier 3 tables: reads tenant-scoped and UNGATED, writes Tier 3 gated — the `beds` rule.** The argument for gating reads holds only for a tenant that never had the tier; it fails for one that had it and was downgraded, which is the case worth designing for. **`blood_units` is the strongest example: a unit reserved for a patient in theatre must never become invisible because a billing flag changed.** `ot_schedule` holds live clinical commitments; a vanished `insurance_claims` row loses a reimbursement. One rule across all three so a reader never has to remember which behaves which way
- `[2026-08-11]` **`insurance_claims.status` is `draft`/`submitted`/`closed` only.** PRD §8 rules out adjudication *entirely*, not just for this phase, so there is deliberately no `approved`/`rejected`/`appealed`/`settled`. `closed` means the clinic stopped working the claim, not that a payer decided anything. Asserted in the suite by confirming `status='approved'` is rejected
- `[2026-08-11]` **`lab_tech` deferred again, now on repo evidence rather than as a punt.** PRD §6 defines no lab-technician persona and Architecture.md §6 lists `profiles.role` as doctor/nurse/billing/admin/patient. Adding the enum value is cheap; making it *useful* is not — adding it to `is_tenant_staff()` would silently grant a technician read access to `invoices`, `billing_line_items` and `prescriptions`, and doing it properly means a parallel set of narrow policies across five tables, which is a feature with its own contract and isolation suite. In a clinic of this size the nurse does sample handling, which is what Phase 3 implemented
- `[2026-08-11]` **`npm run audit:codes` added — mechanical error-code drift detection.** Cross-checks every `'code', 'X'` returned by SQL and every `errorResponse('X')` in an Edge Function against every code documented in `docs/contracts/*.md`, both directions, and exits non-zero on anything undocumented. Doing this by eye across ~33 client-callable functions and 11 contract files is the kind of check that passes on the day it is performed and rots afterwards. It found 10 undocumented codes on first run, including three reachable since Phase 2

## 6. Known Issues / Open Risks

*(Running list — add when discovered, remove when resolved with a note on how)*

**Blockers**
- ~~Migrations not applied to the hosted project~~ — **RESOLVED 2026-08-11.** Jeet supplied `SUPABASE_DB_PASSWORD`; all Phase 1 migrations are pushed and `database.types.ts` is generated. Note the resolution was a **DB password, not an access token**: `supabase link` and the Management API still do not work on this machine, so pushes use `--db-url` against the `aws-0-ap-south-1` pooler
- **No personal access token (`sbp_…`) on this machine.** Consequences: (a) Supabase **Edge Functions cannot be deployed** — `supabase functions deploy` requires a token, so the two Phase 2 PDF functions are written and committed but not live; (b) Auth/project *settings* cannot be changed programmatically, only read

**Phase 2 — business decisions needed from Jeet**
- **`tenants.gst_registered` must be confirmed per real pilot clinic.** It defaults to FALSE, which is the safe default (no tax lines computed, invoice renders as a bill of supply). Whether a clinic actually charges GST depends on its registration, which depends on turnover — ₹20 lakh threshold generally, ₹10 lakh in some special-category states. **This cannot be determined from code.** Getting it wrong in either direction produces a legally incorrect invoice: a non-registered clinic issuing a GST invoice, or a registered one omitting tax. Confirm before any clinic bills a real patient
- **HSN/SAC codes are not populated on the seeded drugs.** The column exists and prints on the invoice, but the starter drug list leaves it null. A GST invoice for medicines really wants it. Needs a data pass, not a code change

**Phase 2 — bugs found and fixed (recorded because both were near-misses)**
- ~~`check_prescription_safety()` returned `requires_acknowledgement: null` on a clean check~~ — **FIXED.** `NULL = 'high' OR false` evaluates to NULL in SQL, so the one field that must never be ambiguous was shipping a null in a safety-critical boolean. Now `coalesce`d. Caught by the local suite
- ~~Deleting any user who had accepted an invite was impossible~~ — **FIXED in `20260811061300`.** A latent Phase 1 bug: `invites.accepted_by` is `ON DELETE SET NULL` while `invites_acceptance_consistent` required `accepted_at`/`accepted_by` both-or-neither, so the FK's own cascade action was guaranteed to violate a constraint on the same row. GoTrue surfaced it only as "Database error deleting user". Relaxed to "accepted_by set implies accepted_at set"; the spent-token guarantee is unchanged. **It stayed hidden because a first `db:seed:reset` has no users to cascade — it only appears on the second run.** Lesson: idempotent tooling has to be run twice to actually be tested
- Related: `db:seed:reset` now dismantles Phase 2 clinical/billing data in dependency order before deleting users, because the `ON DELETE RESTRICT` protecting medical records (correctly) blocks user deletion. Verified by running `--reset` twice

**Phase 2 — known limitations**
- **The drug reference is a starter dataset, not clinically reviewed.** 50 drugs, 25 interaction pairs. Absence of a finding is not evidence of safety — which is why the check returns `partial` the moment a prescribed drug falls outside the list. **Needs clinical review or a licensed data source before a real clinic prescribes against it**
- **Allergy matching is textual** against free-text `patients.allergies`, so it can false-positive (a note reading "no penicillin allergy" matches the penicillin tag). Deliberately biased that way — a spurious warning beats a missed allergy — and every finding carries `match_basis` so the clinician can judge. Structured allergy capture is the real fix
- **PDF rendering cannot display Devanagari.** pdf-lib's standard fonts are WinAnsi-encoded; unrepresentable characters degrade to `?` rather than throwing, so the document still generates. PRD §7 requires Hindi in the UI, so the app will be localised before its PDFs are. Needs an embedded Unicode font (Noto Sans Devanagari + fontkit) — a real bundle-size decision, Phase 3
- **PDF rendering itself is unverified.** The data layer behind both PDFs is covered by the suites; the layout code has never executed, because deploying needs a PAT and running locally needs Docker
- ~~**`visits` is not in the `supabase_realtime` publication yet**~~ — **RESOLVED in Phase 3 (`20260811071100`).** `visits`, `vitals`, `tasks`, `lab_orders` and `lab_results` are all published, verified on the hosted project by `npm run verify:catalog`. Note for Prince: `visits` now emits a change whenever a nurse records vitals (the freshness trigger touches it), so a queue subscriber will see events for encounters whose queue state did not move — re-render from the delivered row
- **Clinical note edits overwrite in place** — no amendment history. Belongs with the Phase 4 audit log

**Phase 3 — bugs found and fixed (all three recorded; two were latent, one is Phase 2's)**
- ~~`rounds_overview` returned only the newest `vitals` row~~ — **FIXED in `20260811071200`.** This contradicted the deliberate nullable-measurement design one migration earlier: a temperature recorded at 10:00 disappeared from the rounds card the moment a BP-only row was saved at 10:05, and a blank field on a clinical glance view reads as "not measured". Now each measurement is the latest known non-null value for the encounter, plus `vitals_component_times` so a composite card is detectable. **Caught by the REMOTE suite, not the local one** — the local fixture happened to insert the fullest observation set last, so the newest row was also the most complete. That is the argument for having both layers. (Aside: `create or replace view` cannot reorder or rename view columns, so the fix needed an explicit DROP + CREATE, which also discards grants and options — both restated in the migration)
- ~~`db:seed:reset` could not delete an invoice that had line items~~ — **FIXED in `20260811071300`. This is a Phase 2 defect, latent since `20260811060700`.** `billing_line_items → invoices` is a composite FK `(invoice_id, tenant_id)` with a bare `ON DELETE SET NULL`, and on a composite FK that nulls **every** referencing column — including the NOT NULL `tenant_id`. So the documented behaviour ("a deleted draft invoice releases its lines back to pending") had never worked; the delete failed outright with `23502`. Fixed with the PG15+ column-list form, `ON DELETE SET NULL (invoice_id)`, which delivers the original intent. **This is the third instance of one bug family** — the Phase 1 invites bug was the first, and Phase 3's migrations avoided the second by choosing RESTRICT for every composite FK to `profiles`. Worth internalising: *any* `SET NULL` on a composite FK whose `tenant_id` is NOT NULL is broken unless it names its columns
- ~~`npm run db:seed` (no `--reset`) crashed on a populated project~~ — **FIXED.** Two separate faults in the idempotent recovery path: `.maybeSingle()` on an unfiltered `profiles` select returned 4 rows for a tenant admin (who can read their whole clinic) and errored; and `create_invite` returning `INVITE_ALREADY_EXISTS` was unhandled, so a run interrupted between minting and accepting an invite could never complete. Both unreachable on a first run and under `--reset`, which is why they survived three phases. **Same lesson as the invites bug, now confirmed twice: idempotent tooling has to be run twice to be tested at all**

**Phase 3 — known limitations**
- **The critical-value reference set is 14 adult thresholds and is NOT clinically reviewed.** Absence of a flag is not evidence a result is safe, which is why an unknown test yields `no_reference` + `requires_manual_review` rather than a clean pass. **PAEDIATRIC AND NEONATAL LIMITS DIFFER MATERIALLY** — the seeded bilirubin threshold is adult-only and would be actively misleading for a newborn. Age-stratified ranges need a real model. Troponin is deliberately absent because its cut-offs are assay-specific
- **A missing `unit` on a lab result is assumed to be the reference unit.** Pragmatic (refusing to evaluate every result with a blank unit box would mean almost nothing got checked) but it is an assumption in a safety path. The lab-entry UI should prefill `unit` from `lab_critical_ranges`, which is readable. An incompatible unit *is* refused as `unit_mismatch`
- **No IPD billing at all.** Admission raises no charge; there is no bed-day rent, no rate card, no ward/bed classification (ICU vs general). This is the largest functional gap for a real IPD pilot and it is bigger than it looks — per-day charging needs a scheduled job, which nothing in this stack currently has
- **No discharge summary.** `discharge_patient()` echoes `p_notes` back but does not store it
- **No dose scheduling.** `prescription_items.frequency` is free text (`'TDS'`), so administrations are logged against an *item*, not a scheduled occurrence, and "this drug is due at 08:00" cannot be computed. Also means administering does not auto-close a `medication_due` task
- **No `lab_tech` role**, though Architecture.md §3 assumes one for the lab queue view. Nurses record results. Cheap to add in Phase 4 alongside the audit log
- **One order = one test.** No panels/multi-analyte results, so a CBC means several orders
- **`notify-critical-lab-value` is written but not deployed** (no PAT — same constraint as the Phase 2 PDFs), and it additionally needs a Database Webhook configured in the dashboard, which cannot be done from SQL or the CLI. It also uses the **service role**, the one stated exception in this phase: a webhook carries no user JWT because no user is involved, so the alternative would be a `SECURITY DEFINER` function open to anonymous callers, which is worse. Narrowed to one read of the row the webhook already delivered, behind a shared secret. **The in-app alert path works without any of it**
- **Vitals entered against the wrong encounter cannot be moved** — `visit_id` is not in the update grant, and there is no delete. Needs Phase 4 amendment tooling
- **Medication administrations are append-only** — a mistaken entry cannot be voided. Same Phase 4 dependency
- **Realtime `replica identity` is left at default (primary key)**, so `old_record` is not delivered on updates. Enough for every current surface; changing it costs WAL volume on `visits`, which is now written on every vitals entry, so it should be a deliberate decision if Prince needs it

**Phase 4 — bugs found and fixed**
- ~~The PGlite harness's `auth.uid()` stub threw on an empty claims setting~~ — **FIXED in `supabase-preamble.sql`.** It was `nullif(current_setting(...)::json ->> 'sub', '')::uuid`, which handles the setting being ABSENT but raises `invalid input syntax for type json` when it is present and EMPTY — i.e. an owner/service-role context. Real Supabase `auth.uid()` returns NULL there, so this was a **fidelity gap that hid a whole class of bug**: any trigger calling `auth.uid()` that can fire from an owner-context write would fail locally for a reason that could never happen on the hosted project. Surfaced the moment the Phase 4 audit triggers started firing on service-role writes. `auth.jwt()` already did it correctly; all three functions are now consistent
- ~~`record_audit_event()` could abort the transaction it was auditing~~ — **FIXED.** Actor resolution now degrades to a system event with the SQLSTATE preserved. The original wrote the right comment ("an audit write must never be why a legitimate action fails") without implementing it
- **A false alarm worth recording, because the reasoning is the lesson:** while building the revenue view I concluded `invoices.issued_at` was never stamped (billing can write `status` but not `issued_at`, and no RPC sets it) and wrote a migration to fix it. **Phase 2 already handles it** — `guard_invoice_status_transition()` both stamps `issued_at` and rejects illegal regressions; I had grepped the RPC file and not the table migration. The redundant migration was deleted before pushing. The invariant is now asserted in `test:phase4` §0b so nobody re-derives the same wrong conclusion

**Phase 4 — known limitations**
- **The audit log has no retention or archival story.** It grows without bound, with no pruning or partitioning. Needs a policy decision before a pilot generates real volume
- **No read auditing.** Only writes are logged. "Who *viewed* this patient's record" is a genuine DPDP-adjacent question this does not answer, and it is the more expensive half to build
- **The audit log is append-only by privilege, not cryptographically.** A service-role actor could alter history. Tamper-evident logging is a bigger project
- **Clinical and billing writes are not audited** — notes, prescriptions, vitals, medication administrations, lab results, invoices. Scoped down deliberately: it needs a retention story, the redaction boundary judged for ~15 more tables, and several of those are already append-only so a change log would mostly restate them
- **"Multi-Branch" in the phase title is not implemented, and cannot be without a model change.** One tenant is one clinic — `profiles.tenant_id` is single-valued (Architecture.md §9) — so there is no group-level rollup across clinics. A tenant hierarchy does not exist. Flagged as a real gap against the phase name rather than quietly reinterpreted
- **The 05:30 IST day boundary** on every daily metric (see §3). A per-tenant timezone is the fix and it changes queue-numbering behaviour, so it is Phase 5 work
- **Tier 3 tables are structure only and several caveats are safety-relevant**: `ot_schedule` does not prevent double-booking a theatre or a surgeon; `blood_units` has **no compatibility or cross-match checking** and a reservation must not be read as a safety confirmation; nothing auto-expires a blood unit (no scheduled job exists in this stack). All three are stated in `tier3-placeholders.md`
- **Wrong-tier and wrong-role are indistinguishable to a client** on the Tier 3 tables — both `42501`. Deliberate (the database does not disclose which check failed), but Prince must read `tenants.tier` and the user's role to word a message
- **`database.types.ts` is stale** — no Phase 4 tables, views or functions. `supabase gen types` runs in a Docker container and Docker Desktop's WSL integration went down mid-session. One command once it is back: `npm run db:types`

**Security / correctness risks**
- **A deactivated user's existing JWT stays valid until it expires (~1h).** Database access is revoked immediately, so no clinic data is reachable, but the token still authenticates. Client-side forced sign-out is specified in `user-management.md` §4 and is **Prince's to build**. If a hard cut-off is required, that needs an Auth Admin API call with the service-role key from a server action — a deliberate decision, not something to add quietly
- ~~"Confirm email" must be ENABLED~~ — **VERIFIED ENABLED 2026-08-11.** `GET /auth/v1/settings` reports `mailer_autoconfirm: false`, i.e. auto-confirm is off and confirmation is required, so `accept_invite()`'s email-match check has teeth. ## 8. Glossary / Project-Specific Terms

*(Add terms as they come up, so any new AI session or new team member doesn't have to guess)*

- **Tenant** — one clinic/hospital using the system
- **Tier 1/2/3** — feature-activation levels (solo clinic / small hospital / large hospital), same codebase, gated by tenant flag
- **Contract** — a short agreed spec (schema + function signature) written before a feature is built, enabling parallel work
- **RLS** — Postgres Row-Level Security, the enforcement mechanism for multi-tenant data isolation
- **Pending user** — signed up but not yet in a tenant (`profiles.tenant_id IS NULL`, `role = 'pending'`). A normal, indefinitely valid state, not an error
- **SECURITY DEFINER** — a Postgres function that runs as its owner rather than its caller. Used here to read `profiles` from inside `profiles` policies without triggering infinite RLS recursion, and to perform writes clients are deliberately not granted
- **Envelope** — the `jsonb {ok, code, message}` shape every Phase 1 RPC returns. `ok:false` is an explainable business failure; a supabase-js `error` is a transport/auth/RLS problem or a bug
- **Invite token** — a uuid v4 in `invites.token`, delivered out-of-band, acting as a capability: possession plus a matching confirmed email is what authorises joining a tenant
- **PGlite** — PostgreSQL compiled to WebAssembly, run in-process by the local test suites so RLS can be verified with no Docker and no credentials
- **UHID / `patient_number`** — the per-tenant serial patients are identified by at the front desk. Restarts at 1 for each clinic; a uuid is unusable for someone reading a paper slip
- **Token / `queue_number`** — the per-tenant, per-**day** OPD queue number. Resets each morning
- **Pending charge** — a `billing_line_items` row with `invoice_id IS NULL`. "Pending charges" is therefore a query, not a status field that could drift
- **`is_auto`** — marks a charge captured automatically by a trigger rather than typed by billing staff. Phase 2's Definition of Done means these should be the norm and manual lines the exception
- **Bill of supply** — the document a clinic that is *not* GST-registered must issue: no GSTIN, no tax section at all. Distinct from a GST invoice showing zeros, which would misrepresent registration status
- **`exempt` vs `non_gst`** — both carry a zero rate but mean different things. `exempt` = a GST-registered clinic supplying an exempt healthcare service. `non_gst` = the clinic is not registered, so GST does not apply at all
- **Rate-wise tax summary** — `invoice_tax_lines`, one row per (category, rate) on an invoice. `invoices.tax_total` is the sum of these, never a rate applied to `subtotal`
- **`partial` safety check** — the check ran but could not see everything (a drug outside the reference list, or an empty allergy history). Must be surfaced as "verify manually"; it is not a clean result
- **Negative control** — the step in each isolation suite that disables RLS, confirms the cross-tenant leak actually appears, then re-enables it. Proves the passing assertions are not vacuous
- **`care_setting`** — the OPD/IPD axis on `visits`, deliberately separate from `visits.status` (the consultation lifecycle). "Currently an inpatient" is `care_setting='ipd' and discharged_at is null`; **a discharge does not touch `status`**
- **`last_vitals_at`** — server-derived cache of the newest observation time on `visits`. Two jobs: cheap "fresh vs overdue" sorting, and making a nurse's vitals entry emit a Realtime change on `visits` so an open rounds view updates with no separate fetch. A cache of *freshness only* — it holds no measurement values, because billing can read `visits`
- **Latest known value** — how `rounds_overview` reports each measurement: the most recent non-null value for that measurement in the encounter, resolved per field. So a NULL means "never recorded", not "absent from the newest row". `vitals_component_times` gives each value's own timestamp, because the displayed set can be a composite of different moments
- **`requires_manual_review`** — generated boolean on `lab_results`, true whenever `critical_check_status <> 'evaluated'`. The second half of the critical flag: `is_critical` says "dangerous", this says "we could not tell". **Both false is the only reassuring combination**; a UI reading only `is_critical` renders every unevaluable result as fine
- **`TIER_NOT_ENABLED`** — the Tier-gate refusal. Its own code, not a generic permission error, because the UI must be able to say "upgrade to enable inpatient management" rather than "you are not allowed". Carries `required_tier` and `current_tier`
- **`PATIENT_MISMATCH` vs `PATIENT_CODE_UNRECOGNISED`** — the scanned band resolved to a *different* patient, versus resolved to *nobody*. Deliberately distinct: one is a wrong-bedside event needing a hard interrupt, the other is an unreadable scan needing a re-scan. Neither is a pass
- **Sample-collection card** — the `sample_collection_due` task a lab order auto-creates on the nurse board. Named in Architecture.md §3, which is why it is a first-class `task_type` rather than a hand-labelled custom task
- **Catalogue check** — `npm run verify:catalog`. Asserts the facts supabase-js cannot see: Realtime publication membership, RLS actually enabled, `security_invoker` on views, withheld column grants, revoked EXECUTE. All of these fail *silently* if lost, which is why they get their own suite
